## Passo 2 — Regra escolhida

| Identificador | Regra Checkstyle | Padrão (`format`) | Convenção |
|---|---|---|---|
| Constantes (campos `static final`) | `ConstantName` | `^[A-Z][A-Z0-9]*(_[A-Z0-9]+)*$` | MAIÚSCULAS_COM_UNDERSCORE (Google Java Style / Oracle Naming Conventions), ex.: `MAX_PAGES` |

O workflow corre em cada pull request e falha quando há violações (`fail_level: error`).

## O que o Checkstyle não consegue verificar

O Checkstyle só verifica a forma do nome através de uma expressão regular, por isso não consegue saber se um nome é significativo: `MAX_PAGES` e `XPTO_1` passam ambos, e um nome enganador como `MAX_PAGES = 3` (que na verdade conta tiros) também. Também não percebe a intenção do programador — por exemplo, não sabe se um campo `static final` devia mesmo ser uma constante, nem se dois nomes diferentes representam o mesmo conceito. Por fim, com o reviewdog no modo `added`, só são reportadas as violações nas linhas alteradas pelo pull request, por isso violações antigas no resto do código não fazem o gate falhar.
